# 04 · 模块详解

本文档逐一说明 `scanner/` 下各模块的职责、关键接口与协作关系。完整源码以仓库为准，本文档聚焦「对外契约」。

## 模块总览

```

├── models.py          # 规范数据模型（pydantic）

├── adapters/
```

## 1. `models.py` — 规范数据模型

定义全系统共享的 pydantic 模型：

- `Outcome` — 单个结果（name/price/bid/ask/available_liquidity_usd），校验价格 ∈ [0,1]。
- `FieldStatus` — 枚举 `OK` / `UNAVAILABLE`。
- `CanonicalMarket` — 规范市场，含 `age_seconds` 计算属性、`field_status`、`is_stale`；`category`（市场类目，如 politics/sports/crypto，平台无此概念时为 None）；`cross_refs: Dict[str, List[str]]`（平台名 → 对端市场标识列表）记录平台自报的跨平台关联线索（如 predict.fun 市场标注其对应的 Polymarket conditionId / Kalshi ticker），匹配引擎用作「金标准」关联，默认空，向后兼容。
- `OutcomeAlignment` — 规范结果到各平台原生结果名的映射（含 `inverted`）。
- `EquivalentMarketGroup` — 等价市场组（members + outcome_map + match_confidence）。
- `ArbLeg` — 套利一腿（platform/market_id/outcome/side/price）。
- `ArbitrageOpportunity` — 套利机会（legs/net_profit_margin/recommended_size_usd/detected_at/data_age_seconds）。

## 2. `store.py` — 存储

- `MarketStore`（Protocol）：`upsert(markets)` / `get(platform, market_id)` / `list_all()` / `list_by_platform(platform)` / `replace_platform(platform, markets)`。
- `InMemoryMarketStore`：以 `(platform, market_id)` 为键的 dict 实现。`replace_platform` 原子替换某平台全部市场（增新、删本轮消失的），避免消失市场作为陈旧幽灵无限累积、污染匹配（摄取每成功一轮调用一次）。
- `OpportunityStore`：以 `group_id` 为键，`upsert` / `get` / `remove(group_id)` / `list_all()` / `list_sorted()`（按净利润率降序）。

## 3. `fees.py` — 费用模型

- `FeeModel`（Protocol）：`fee_for(price, contracts) -> float`。
- `FlatFeeModel(rate=0.0)`：`fee = rate * price * contracts`。
- `KalshiFeeModel(coefficient=0.07)`：`fee = ceil(0.07 * contracts * price * (1-price) * 100)/100`。

## 4. `adapters/` — 平台适配器

### `base.py`
- `PlatformAdapter`（runtime_checkable Protocol）：`name`、`async fetch_markets()`、`async refresh_prices(markets)`。
- `AdapterError`：适配器抛出的**唯一**错误类型，携带可选的 `adapter` 名。

### `polymarket.py` — `PolymarketAdapter`
- 通过 Gamma API（`gamma-api.polymarket.com/markets?active=true&closed=false`）**分页**发现市场（`limit`/`offset`，按 `volumeNum` 降序，受 `page_size`/`max_markets` 控制，默认每页 100、上限 200），CLOB API（`/book`）读订单簿。Gamma 默认每页仅 ~20 条，分页后可覆盖数百个最活跃市场，与 predict.fun 产生更多跨平台匹配。
- **按类目优先抓取（数据驱动）**：可配 `categories`（类目 slug 列表，见 `CATEGORY_TAG_IDS`：politics/elections/sports/geopolitics/economy/culture/crypto/tech/business/science，按真实成交量排序）。配置后逐类目按 `tag_id` 成交量降序抓取、在 `max_markets` 内分配预算并去重，把来源类目写入 `CanonicalMarket.category`；不配则全站按量降序翻页。未知 slug 被忽略并退化为全站抓取。实测各主类目成交量：政治 ~$2.6B、选举 ~$2.4B、体育 ~$2.0B、地缘 ~$534M 居前。
- 价格已是 0–1；volume/liquidity 来自 Gamma，已是美元。
- `fee_rate` 取自 `FlatFeeModel`（默认 0.0）。
- bid/ask 从订单簿取（最优买/卖），缺价时回退到 book 中间价。
- 注入 `httpx.AsyncClient` 以便测试用 respx mock。

### `kalshi.py` — `KalshiAdapter`
- 通过 `GET /trade-api/v2/markets` 列市场（游标分页），API 密钥从 `api_key`/`KALSHI_API_KEY` 取，作为 Bearer 头。
- 价格分→概率（÷100），并 clamp 到 [0,1]；volume/liquidity 分→美元（÷100）。
- NO 价为 YES 的补；附 `KalshiFeeModel`。
- 缺密钥时仍可列公开市场（优雅降级）。

### `predictfun.py` — `PredictFunAdapter`（Phase Three · 只读行情）
predict.fun 是建在 BNB Chain 上的链上预测市场（off-chain CLOB 订单簿 + 链上结算，二元 YES/NO、价格 0–1，架构与 Polymarket 高度相似）。本模块只实现**只读行情接入**（满足 `PlatformAdapter`）；下单（链上签名）属后续执行适配器，不在此模块。

- base url：`DEFAULT_BASE_URL="https://api.predict.fun"`、`TESTNET_BASE_URL="https://api-testnet.predict.fun"`（构造参数 `base_url` 可切换测试网）。
- 发现市场：`GET /v1/markets?status=OPEN`（游标分页，`{success, cursor, data:[...]}`）；订单簿：`GET /v1/markets/{id}/orderbook`（`asks`/`bids` 为 `[price, size]`，价格已 0–1）。
- 规范化：产出 YES / NO 两个 `Outcome`（NO 价 = 1 − YES 价），bid/ask 取订单簿最优买/卖；`feeRateBps`（基点）÷10000 → `fee_rate`；**流动性**从订单簿全档深度估算（Σ 各档 price×size，买卖两侧合计，`_book_depth_usd`），订单簿缺失时标记 `UNAVAILABLE`；**成交量**列表端点 `stats` 当前为空、`statistics` 端点不存在（404），防御性从 `stats` 提取（`_extract_volume`，将来 API 填充自动生效），否则诚实标记 `UNAVAILABLE`。
- 可选鉴权：携带 `x-api-key`（构造参数 `api_key` 或 `PREDICTFUN_API_KEY` 环境变量），缺失时仍尝试公开读取（优雅降级）。下单所需的钱包签名/JWT 不在只读适配器内。
- **跨平台关联（关键）**：把市场自报的 `polymarketConditionIds` / `kalshiMarketTicker` 写入 `CanonicalMarket.cross_refs`，供匹配引擎作「金标准」关联（见 §7）。

> 三个适配器都通过 `tests/adapter_contract.py` 的共享**一致性套件**（Req 7.2）。

## 5. `ingestion.py` — `IngestionService`

```python
IngestionService(adapters, store, *, refresh_interval=30,
                 fetch_timeout=30, staleness_threshold=60, clock=None)
```
- `run()`：每适配器一个 `asyncio` 循环。
- `_cycle(adapter)`：抓取 → 打时间戳 → 入库 → 重算过期；超时/异常被隔离并保留上一份正常数据。**成功抓取后用 `store.replace_platform` 原子替换该平台市场**（删除本轮消失的，防陈旧幽灵累积）；抓取失败则保留旧数据不误删。
- 适配器**自愈**：`PolymarketAdapter`/`PredictFunAdapter` 在传输层错误时重置内部 `httpx` client，使退避重试与熔断半开探测用全新连接恢复（修复休眠/断网后摄取永不恢复的稳定性 bug）。
- 构造时校验 `refresh_interval ≤ 60`、各参数为正。

## 6. `ranking.py` — `RankingService`

```python
rank(markets, *, by: "volume"|"liquidity",
     min_volume=None, min_liquidity=None) -> list[CanonicalMarket]
```
按所选指标降序排序；阈值过滤；指标不可用（None）的市场排最后，且被激活的阈值排除。不修改输入列表。

## 6b. `resilience.py` — 数据接入韧性（Phase Two · 切片 C）

把限流、退避、熔断做成与适配器解耦的横切能力，通过 `ResilientAdapter` 包装任意 `PlatformAdapter`，核心与具体适配器零改动。

- `RateLimiter(min_interval, clock, sleep)`：令牌桶/最小间隔限流，`acquire()` 保证相邻调用间隔 ≥ `min_interval`（Property 15）。
- `Retry(max_attempts, backoff_base, sleep)`：对 `AdapterError` 指数退避重试，`run(op, name)` 调用次数 ≤ `max_attempts`（Property 16）；非 `AdapterError` 不重试。
- `CircuitBreaker(failure_threshold, reset_timeout, clock)`：状态机 `CLOSED → OPEN → HALF_OPEN`（Property 17）。连续失败达阈值熔断；冷却期内 `allow()` 返回 False（快速失败，不触达底层）；冷却后半开放行一次探测，成功闭合、失败重新熔断。
- `AdapterMetrics`：成功/失败/限流/熔断拒绝计数 + 熔断状态 + 最近错误/成功时间，供 `/health` 汇报。
- `ResilientAdapter(adapter, *, min_interval, max_attempts, backoff_base, failure_threshold, reset_timeout, clock, sleep)`：对外仍是 `PlatformAdapter`；`_guard` 流程 = 熔断检查 → 限流 → 退避重试包裹底层调用，并更新 `metrics`。熔断打开时抛 `AdapterError`，沿用既有故障隔离语义。

接入：`build_application` 对**从配置构造**的适配器统一包装（注入的适配器保持原样）；`/health` 通过 health_provider 汇报熔断状态与计数。开关见配置 `scanner.adapter_*` / `scanner.circuit_*`。

## 7. `matching.py` — `MatchingEngine`

- 文本工具：`normalize_text` / `tokenize` / `extract_entities`。
- `SemanticSimilarity`（Protocol）+ `LexicalSimilarity`（词法默认）。
- 相似度后端（Phase Two · 切片 D，均零外部依赖）：
  - `EmbeddingSimilarity(encoder)` — 注入式编码器（`str -> 向量`），计算两个标题向量的余弦相似度并线性映射到 [0,1]（`(cos+1)/2`）。不强依赖任何嵌入库，可注入 sentence-transformers / OpenAI embedding / 确定性假编码器（测试用）；任一标题编码为零向量时返回 0.0。
  - `HybridSimilarity(semantic, *, lexical=None, lexical_weight=0.5)` — 把词法与语义后端按权重融合，兼顾召回与稳健兜底。`lexical_weight ∈ [0,1]`，语义权重为 `1 - lexical_weight`；两后端分数均在 [0,1]，融合结果亦在 [0,1]。
  - `NormalizingLexicalSimilarity(*, normalizer=None, ...)` — 继承 `LexicalSimilarity`，分词后先用 `SynonymNormalizer` 把同义/缩写词归一到规范词，再做 token-set 比较，从而提升等价市场召回、减少漏信号。是默认词法的「即插即用」增强（由配置 `similarity_backend="normalizing"` 选用）。
- `Blocker.candidate_pairs(markets)`：生成去重、确定性排序的跨平台候选对。
- `ScoreWeights`、`composite_score(a, b, similarity, weights)`、`map_outcomes(members)`。
- **赛段/范围限定词闸门**（`_scope_signature` / `_scope_mismatch`，真实数据修复）：把标题归一为「赛段签名」——小组赛及组别（group:a..）、淘汰赛轮次（ro16/ro32/quarterfinal/semifinal）、进程（advance/qualify）。两个市场赛段签名不一致即判**不同事件**，`composite_score` 直接返回 0（同时保护 cross_ref 与普通评分两条路径）。修复了「夺冠 vs 赢小组」因仅差几个词、词法相似度 ~0.86 被误判等价而产生的虚假套利。
- **数字/阈值/日期闸门**（`_number_mismatch` / `_significant_numbers`）：归一标题中显著数字（行权价/次数/年份，处理 $、逗号、k/m/b 后缀），集合不一致即判**不同事件**返回 0。防御「4 次 vs 7 次降息」「$100k vs $110k」「2025 vs 2026」这类数字差异被加权评分淹没的同类错配。
- 设计原则（见 [13-匹配算法重设计与正确性红线.md](./13-匹配算法重设计与正确性红线.md)）：身份决定性维度（赛段、数字阈值、日期）用**硬 veto**而非软加权——错配会真亏钱，漏配只是错过，故宁可漏不可错。
- `MatchingEngine(similarity, blocker, weights, score_threshold).match(markets) -> list[EquivalentMarketGroup]`：分块 → 评分 → 映射 → 分组，按置信度降序输出。相似度后端由 `app.py` 按配置 `similarity_backend` 选择（`"normalizing"` 用 `NormalizingLexicalSimilarity`，否则默认 `LexicalSimilarity`）。

### 跨平台金标准关联（Phase Three）

当平台自报跨平台关联线索（写入 `CanonicalMarket.cross_refs`，如 predict.fun 市场标注其对应的 Polymarket conditionId）时，这比标题语义可靠得多，匹配引擎据此走「金标准」短路：

- `_cross_referenced(a, b)`：两市场只要通过 `cross_refs` 任一方向互指（`a.cross_refs[b.platform]` 含 `b.market_id` 或反之）即返回 `True`。
- `composite_score`：互指时**短路返回 `1.0`**（满分置信度），不再计算标题/实体/结构/日期的加权分。
- `Blocker.keys_for`：新增 `xref` 分块键——每个市场生成「指向自己」的键 `xref:{平台}:{市场id}`，以及它「引用对端」的键 `xref:{对端平台}:{对端id}`。当 A 的 `cross_refs` 指向 B 时，A 产生的 `xref:{B平台}:{B_id}` 与 B 自身产生的同名键命中同一候选块，使互指但标题措辞完全不同的市场也能落入同一块、进入评分。

## 7b. `synonyms.py` — 词条归一（Phase Two · 切片 D 信号质量）

跨平台等价市场常用不同措辞描述同一事件（如 `POTUS` vs `president`、`BTC` vs `bitcoin`），纯词法相似度会因此漏配、漏信号。本模块提供轻量、确定、零外部依赖的同义词/缩写归一表，供 `NormalizingLexicalSimilarity` 在分词后归一。

- `DEFAULT_SYNONYM_GROUPS`：`规范词 -> 变体列表` 词典，刻意保持小而高置信（只收录歧义低、跨平台高频的金融/政治/体育术语），如 `bitcoin: [btc, xbt]`、`president: [potus, presidential]`、`above: [over, exceed, ...]` 等。
- `SynonymNormalizer(groups=None)`：构造时把词典展开成「任一词 -> 规范词」查表；`normalize(token)` 把单个词条映射到规范词（未收录原样返回），`normalize_all(tokens)` 批量归一。运营者可通过 `groups` 参数扩展或替换词典。

> 它是「增强词法」与「真正 embedding 语义后端」之间的务实折中——后者可随时通过实现 `SemanticSimilarity` 接口接入。

## 8. `arbitrage.py` — `ArbitrageEngine`

```python
ArbitrageEngine(fee_models: dict[str, FeeModel], confidence_threshold=0.0,
                default_fee_model=FlatFeeModel(), clock=..., staleness_threshold_seconds=None)
```
- `evaluate(groups) -> list[ArbitrageOpportunity]` / `evaluate_group(group)`。
- 跳过过期组（Property 5）与低置信度组（Property 7）；逐结果选最低 ask；计入费用算净利润率；按最薄腿流动性限规模；记录含 ≤0 利润率的机会。

## 9. `opportunities.py` — `OpportunityService`

```python
OpportunityService(store=OpportunityStore(), min_net_profit_margin=0.0)
```
- `reconcile(opportunities)`：全量对账——upsert 可列出的（margin>0 且 ≥阈值）、移除失效的（≤0、低于阈值、或本轮消失的组），返回过滤排序后的列表。
- `list()`：防御性地再过滤排序，保证 Property 10（降序、无 ≤0）。

## 10b. `signals.py` — `SignalService`（Phase Two · 切片 A）

把无状态的瞬时机会提升为**有状态的信号**，建立完整生命周期与事件流——信号工具的核心产物。

- `SignalStore`（Protocol）：`get_active` / `list_active` / `upsert_active` / `remove_active` / `append_event` / `list_events`。
- `InMemorySignalStore`：活跃信号用 dict（键 group_id）、事件流用 list 追加的内存实现。
- `SqliteSignalStore(path="signals.db")`（Phase Two · 切片 B）：基于标准库 `sqlite3` 的持久化实现，零外部依赖、可文件落盘。两张表 `active_signals`（按 group_id upsert，关闭即删行）与 `signal_events`（只追加，自增 id 保序）；信号/事件用 pydantic `model_dump_json()` 整体序列化。**重启恢复无需额外逻辑**——活跃信号天然在表中，调用方零改动。传 `:memory:` 得到进程内库（测试用）。
- 存储选择由配置 `scanner.signal_store_path` 决定：`None`→内存；文件路径→SQLite。
- `SignalService(store, clock)`：
  - `reconcile(opportunities) -> list[SignalEvent]`：每周期用「可列出的机会快照」对账信号状态——
    - 新出现 group → 开 `OPEN` 信号 + `OPENED` 事件；
    - 仍存在 group → `SUSTAINED` + `UPDATED` 事件，刷新净利润率/规模/`last_seen_at`，`peak_net_profit_margin` 单调不减；
    - 消失 group → `CLOSED` 事件 + 从活跃集合移除。
  - 接入点：`ScannerApplication.run_pipeline_once()` 在机会对账之后、发告警之前调用。

相关模型（`models.py`）：`SignalStatus`（OPEN/SUSTAINED/CLOSED）、`SignalEventType`（OPENED/UPDATED/CLOSED）、`Signal`（含 `duration_seconds`、`is_active`、`peak_net_profit_margin` 等）、`SignalEvent`。

对应 API：`GET /signals`、`GET /signals/events`，详见 [05-API文档.md](./05-API文档.md)。

## 10c. `execution.py` — 执行边界（Phase Three · 切片 E）

与只读的 `PlatformAdapter`（读边界）对称的**写边界**，是交易半边的地基。

- `ExecutionError(message, *, platform=None)`：执行适配器抛出的统一错误类型（与读边界的 `AdapterError` 对称）。
- `ExecutionAdapter`（runtime_checkable Protocol）：`name`、`async place_order(*, market_id, outcome, side, limit_price, quantity)`、`async cancel_order(platform_order_id)`、`async get_order(platform_order_id)`、`async get_balance()`、`async get_positions()`。执行引擎只依赖本接口，新增交易平台无需改动引擎与风控。
- `FillPolicy` / `full_fill_at_limit`：成交模拟策略（限价, 数量 → 成交数量, 成交价）。
- `PaperExecutionAdapter`（模拟盘，**不动真钱**）：内存维护虚拟余额与持仓，按 `fill_policy` 模拟成交；可注入 `reject_markets`（拒单）与自定义 `fill_policy`（部分成交/不成交）以测试执行引擎的双腿原子性与补救逻辑（切片 F）。下单扣余额、更新持仓（同 `(market_id, outcome)` 数量加权平均价）；余额不足/拒单抛 `ExecutionError`。注入 `clock` 使时间戳确定。

相关模型（`models.py` · 交易域）：`OrderSide`、`OrderStatus`、`TradePlanStatus`、`Order`、`Fill`、`Position`、`TradeLeg`、`TradePlan`。

> 安全：鉴权凭证（API 密钥/私钥）只存在于具体执行适配器内部（经环境变量注入），绝不进入交易域模型、日志或 API 响应。真实平台执行适配器（Kalshi）见切片 I，默认 dry-run。

## 10d. `execution_engine.py` — 套利执行引擎（Phase Three · 切片 F）

交易系统**风险最高**的部分。把套利机会落成双腿计划并执行，核心职责是保证**双腿原子性**——绝不放任单边裸敞口。

- `ExecutionEngine(adapters: dict[平台名, ExecutionAdapter], clock)`：
  - `build_plan(opportunity, *, size_usd) -> TradePlan`：把 `ArbitrageOpportunity` 落成双腿 `TradePlan`。套利买**等量合约** `N = size_usd / 每对成本`（各腿目标价之和），各腿同 N，确保真正对冲且总投入不超过 `size_usd`（修复了此前「每腿 size_usd/腿价」导致部署 2×预算且合约数不等的缺陷）。
  - `async execute_plan(plan) -> TradePlan`：逐腿下单；**全部腿成交 → `COMPLETED`**；任一腿失败/未完全成交 → 进入**补救**（对已成交的腿反向卖出平仓），计划置 `FAILED`，在 `notes` 记录补救动作与任何**残余敞口**。
  - `has_residual_exposure(plan) -> bool`：计划是否留有单边裸敞口（供告警/健康检查）。
  - **已实现收益核算（任务 2）**：执行（非 dry-run）后按**实际成交价**核算 `realized_profit_usd` 等字段——对冲赔付（各腿成交量最小值 × $1）− 实际成本（Σ 成交量×成交均价）。用于审计「检测为正的套利按实际成交价是否真赚」（滑点/费用可能使其实亏，标记 `is_genuinely_profitable=False`）。`last_orders` 暴露已成交订单供持久化对账。
- 补救逻辑确保:即使一腿成交后另一腿失败,也会尝试平掉已成交腿;若平仓也失败则明确标记「残余敞口」并 `logger.error`,需人工介入。
- **dry-run 安全开关（Phase 3 · 切片 G）**：`execute_plan(plan, *, dry_run=False)`，`dry_run=True` 时**只演练不真正下单**——遍历各腿把「将要下的单」记入 `notes`（`[DRY-RUN]` 前缀），绝不触达任何执行适配器、绝不动真钱、不产生真实订单，计划置 `COMPLETED`。这是生产前验证的核心安全机制。

## 10d-2. `risk.py` — 风控闸门（Phase Three · 切片 G）

真实资金安全是最高原则——任何能下单的代码 bug 即亏损。本模块在「检测到机会」与「真正下单」之间插入一道**确定、可测、可解释**的风控闸门，是真实交易的硬前置。

- `RiskLimits`（frozen dataclass）：风控阈值，默认偏保守——`max_trade_size_usd=100`、`max_market_exposure_usd=200`、`max_total_exposure_usd=1000`、`max_slippage=0.02`、`min_net_profit_margin=0.02`、`max_data_age_seconds=30`、`dry_run=True`、`require_confirmation=True`。负值阈值构造即报错。由配置 `risk.*` 段映射（`config.py` 的 `RiskConfig.build()`）。
- `RiskCheck` / `RiskDecision`：单条检查结果（name/passed/detail）与整体决策（approved / approved_size_usd / dry_run / require_confirmation / 各检查明细），`to_dict()` 可 JSON 序列化、`rejected_reasons` 列出未通过项，供告警/UI。
- `RiskManager.evaluate(opportunity, *, current_total_exposure_usd, market_exposure_usd, available_balance_usd, observed_prices)`：对一个候选机会逐条校验（任一拦截即整体拦截）——
  1. **最小净利润率**：扣费后净利润率 ≥ 门槛。
  2. **信号新鲜度**：数据年龄 ≤ 上限（过期价格不交易）。
  3. **滑点保护**：提供实时观测价时，各腿实际可成交价偏离信号价不得超过 `max_slippage`。
  4. **单笔规模上限**：核准规模 ≤ `max_trade_size_usd`。
  5. **单市场敞口上限**：核准规模 ≤ 该市场剩余敞口余量。
  6. **总敞口上限**：核准规模 ≤ 总剩余敞口余量。
  7. **余额充足**：提供余额时，余额必须覆盖核准规模（不足直接拦截，不悄悄缩小规模）。
  - **核准规模**取「机会建议规模」与单笔/单市场/总敞口余量的最小值；任一上限无余量（核准 ≤ 0）即整体拦截。
- 设计取向：纯函数式闸门——给定机会与当前敞口/余额/观测价快照，返回可序列化、可解释的决策。不持有状态、不触达平台，因此完全确定可测。敞口/余额由调用方（切片 H 编排层）提供。

> **dry-run（默认开启）**：`RiskLimits.dry_run` 透传到 `RiskDecision.dry_run`，下游 `ExecutionEngine.execute_plan(dry_run=...)` 据此只演练不下单。真实下单必须显式 `dry_run: false` 且接入真实执行适配器（切片 I）+ 经人工确认（切片 H）。

## 10e. `trade_store.py` — 交易持久化（Phase Three · 切片 F）生产交易必须可审计。沿用 `SignalStore` 的接口化 + SQLite 风格：

- `TradeStore`（Protocol）：`upsert_plan` / `get_plan` / `list_plans` / `upsert_order` / `get_order` / `list_orders`。
- `InMemoryTradeStore`（开发/测试）、`SqliteTradeStore(path="trades.db")`（持久、跨重启可恢复，`:memory:` 可用于测试）。订单/计划用 pydantic `model_dump_json()` 整体序列化，便于事后对账与故障复盘。

## 10e-2. `trading.py` — 半自动交易编排（Phase Three · 切片 H）

把切片 G 的风控闸门真正串进流程：机会 → 风控 → 待确认计划 → 人工确认 →（dry-run）执行。**绝不自动下真单**。

- `TradingService(*, risk_manager, execution_engine, store=InMemoryTradeStore(), clock)`：
  - `propose(opportunities, ...)`：每周期对可交易机会跑风控；通过的用 `execution_engine.build_plan` 生成 `PENDING_CONFIRMATION` 计划（规模来自风控核准）并持久化，风控决策记入 `notes`；不通过的记录被拒原因。**去重**：同一 group 已有未终结计划时不重复生成。**敞口自核算**：从未终结/已完成计划估算当前总敞口与各市场敞口（`_current_exposure`），并在同一周期内累计新计划敞口传入风控，使总/单市场敞口上限真正生效。返回本次新生成的计划。
  - `async confirm(plan_id)`：人工确认 → 计划置 `CONFIRMED` → 立即按风控 `dry_run` 标志调 `execute_plan`（dry-run 只演练不下单）→ 持久化最终状态。计划不存在抛 `KeyError`，非待确认状态抛 `ValueError`。
  - `reject(plan_id)`：人工拒绝 → 计划置 `REJECTED`（同样的存在性/状态校验）。
  - `list_plans(status=None)` / `get_plan(plan_id)` / `list_orders()`：查询（按创建时间升序，可按状态过滤）。
- 接入：`run_pipeline_once()` 在信号对账后调 `propose(listed)`（异常隔离，不中断主流水线）；`build_application` 用 `PaperExecutionAdapter`（模拟盘，不动真钱）装配执行引擎、按 `risk` 配置构造 `RiskManager`、按 `scanner.trade_store_path` 选择内存/SQLite 交易存储。
- 对应 API：`GET /trade/plans`、`GET /trade/plans/{id}`、`POST /trade/plans/{id}/confirm`、`POST /trade/plans/{id}/reject`，详见 [05-API文档.md](./05-API文档.md)；仪表盘「交易计划」卡片可直接确认/拒绝。

> ⚠️ 安全：默认 dry-run + 需人工确认 + 仅模拟盘执行适配器，三重保险。真实下单需接入真实执行适配器（切片 I）+ 显式关闭 dry-run + 交易 API 鉴权（硬前置）。

## 10f. `history.py` — 行情/机会历史时间序列（Phase 3 · 切片 K）只读快照（行情、机会）本身瞬时、放内存即可，但**历史时间序列**有产品价值：画某个套利机会的净利润率走势、回看信号触发时的价差。本模块沿用接口化 + SQLite 风格，记录每个检测周期的轻量采样点，并设保留窗口防止无限膨胀。

- `HistoryPoint`（dataclass）：通用采样点（`key` 标识 + `label` 展示名 + `value` 值 + `at` 时间戳）。
- `HistoryStore`（runtime_checkable Protocol）：`record_opportunities` / `record_markets`（每周期写入）、`opportunity_series(group_id, limit)` / `market_series(platform, market_id, limit)`（查询，按时间升序便于直接画图）。
- `NullHistoryStore`：不记录任何历史的空实现（未配置 `history_store_path` 时使用，调用方零分支）。
- `SqliteHistoryStore(path="history.db", *, retention_days=7.0, clock=...)`：SQLite 实现，两张表 `opportunity_history`（group_id / label / margin / ts）与 `market_price_history`（platform / market_id / label / price / ts），均带 `(key, ts)` 索引。
  - `record_opportunities`：每周期每个机会组写一行净利润率；写入后**机会性裁剪**超出保留窗口（默认 7 天）的旧行。
  - `record_markets`：每周期每个市场写一行 YES 价（无 YES 结果时取首个结果价）。
  - 注入 `clock` 使时间戳/裁剪确定（测试用）。
- 存储选择由配置 `scanner.history_store_path` 决定：`None`/空→`NullHistoryStore`（不记录）；文件路径→`SqliteHistoryStore`。保留窗口由 `scanner.history_retention_days` 配置。

接入：`run_pipeline_once()` 在机会对账后调用 `record_opportunities` / `record_markets` 写入历史。对应 API：`GET /opportunities/{group_id}/history`、`GET /markets/{platform}/{market_id}/history`（未配置历史存储时返回空列表），仪表盘机会行点开即调用前者画净利润率走势 SVG 迷你图（内联零依赖 `sparkline`）。详见 [05-API文档.md](./05-API文档.md)。

## 11b. `observability.py` — 可观测性（Phase Two · 切片 D）

生产级信号工具需要可诊断：知道每个检测周期跑了多久、开了多少信号、当前活跃多少。本模块提供两件轻量、零外部依赖的能力。

- `JsonLogFormatter`：把日志记录格式化为**单行 JSON**（含 `ts` / `level` / `logger` / `message`，异常时附 `exc_info`），便于被集中式日志系统（ELK / Loki）采集与检索。
- `configure_json_logging(level=INFO)`：把根日志切换为 JSON 输出（替换根 logger 的 handler）。**幂等**（先清空已有 handler），可选启用，不影响默认人类可读日志。
- `PipelineMetrics`（dataclass）：流水线运行指标的累计 + 最近快照。
  - `record_cycle(...)`：在每个检测周期结束时调用，累计 `cycles_total` / `signals_opened_total` / `signals_closed_total` / `alerts_fired_total`（单调不减），并刷新 `last_*` 快照（最近一次周期的耗时与各项计数、当前活跃信号数）。
  - `snapshot()`：返回可 JSON 序列化的快照（去掉 `clock`、`last_cycle_at` 转 isoformat），供 `/metrics` 端点。
  - 用注入的 `clock` 计时，使测试确定（不依赖真实墙钟时长）。

接入：`build_application` 按 `settings.json_logging` 调 `configure_json_logging()`，构造 `PipelineMetrics` 并共享给 `create_app` 与 `ScannerApplication`；`run_pipeline_once()` 在周期末尾调用 `metrics.record_cycle(...)`。对应 API：`GET /metrics`，详见 [05-API文档.md](./05-API文档.md)。
