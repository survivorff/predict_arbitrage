### 修复（套利正确性 · Tier-0 · 资金安全）
- **下单前结果极性强校验(缺口 B-1)**：套利对冲性要求两腿买入**真正互补**的结果(恰好一边赔付);极性判反会让「买 YES + 买 NO」退化为「买 YES + 买 YES」= 双倍单边裸赌、真亏钱。此前极性完全依赖匹配阶段 `map_outcomes`(靠标题 not/won't 判断),套利引擎盲信。本轮在 `ArbitrageEngine.evaluate_group` 选腿后加 `_polarity_consistent` **独立交叉校验**:用每条腿**原生结果名**的内在极性,对照其声称服务的规范结果(canonical)与是否反转(inverted),按 `期望极性 = canonical_is_yes XOR inverted` 核对,矛盾即拒绝整笔机会;并要求两腿覆盖不同规范结果(YES+NO 各一)防重复。原生名极性无法判定时不否决(不误杀)。`_ChosenLeg` 新增 canonical_outcome/inverted 字段。新增测试 3 个(对齐搞反/合法反转/重复规范结果),全套 **645 个测试通过**。设计思路见 `docs/15` ADR-005。

### 新增
- **链上 gas 成本核算(缺口 E-1 · 套利净利真实化)**：把链上交易成本计入套利评估。**关键设计**:gas 是**每笔交易/每腿的固定成本,不随仓位规模缩放**(与按名义额缩放的手续费本质不同),若按对摊进 net_margin 会错误地让 gas 随规模放大。故在**整笔交易**层面核算——`扣gas后利润 = recommended_size×net_margin − 腿数×gas_cost_per_leg`,低于 `min_net_profit_after_gas_usd` 则跳过;`ArbitrageOpportunity` 新增 `gas_cost_usd`/`net_profit_after_gas_usd` 字段,经 API 呈现。`config.py`/`config.yaml`/`app.py` 接入,**默认 gas=0(不建模,行为不变,字段为 None 诚实表示"未建模")**,运营者按实际链况配置。新增测试 4 个。设计思路与坑详见新增的 `docs/15-设计决策记录.md` ADR-004。

### 修复（执行安全 · leg risk 降险 · 资金安全）
- **双腿执行加入「先难后易」+「全成或撤(IOC)」(降低单边裸敞口风险)**：套利执行的头号风险是 leg risk——一腿成交、另一腿没成交就留下单边裸敞口。本轮加两道执行防线：
  - **先难后易**：`ExecutionEngine.execute_plan` 改为按各腿**可成交流动性升序**下单(最难成交的腿先下)。若最难的腿失败,此时尚未动用其它腿,无需补救、损失最小;只有最难的腿成了才下较易的腿。
  - **全成或撤(IOC)**：一腿未完全成交即视为失败,并**立即撤掉未成交挂单**(`_kill_remainder`),绝不把挂单留在簿上、避免它在补救完成后才成交而凭空产生新裸敞口;已成交部分仍反向平仓。
  - 为支持排序,`ArbLeg`/`TradeLeg` 新增 `available_liquidity_usd`,由 `ArbitrageEngine` 写入、`build_plan` 透传。
  - 新增测试 4 个(先难后易排序、流动性透传、部分成交 IOC 撤单、最难腿失败不下第二腿)。全套 **638 个测试通过**。同步更新 `docs/14`(leg risk 章节、防线表、路线图)。

### 新增
- **结算日期硬 veto（Tier-0 红线 C「结算等价」缺口修复 · 高 · 资金安全）**：用户核查外星人单时指出 Polymarket「by December 31」与 predict.fun「before 2027」标题不同，担心日期错配。排查发现:该事件下 Polymarket 有**多个子市场共享几乎相同的 question 文本**，真正区分它们的是**结算日期**(endDate 分别为 2026-04-30 / 2026-06-30 / 2026-12-31 ...)——而旧匹配**只比标题文本、完全不用结算日期**(`_date_proximity` 因无日期字段恒返回 0.5 中性值)，存在错配到不同结算窗口子市场、制造跨不同事件虚假套利的风险。修复:
  - `models.py` 的 `CanonicalMarket` 新增 `resolution_date: Optional[datetime]` 字段。
  - `polymarket.py` 从 Gamma `endDate`/`endDateIso` 解析结算日期(`_parse_end_date`)。
  - `predictfun.py` 因 markets 端点无结构化日期字段,从 `description` 文本解析「Month Day, Year」截止日(优先 by/before 之后的日期,`_parse_resolution_date`)。
  - `matching.py` 新增 `_date_mismatch` 硬 veto:两市场都已知结算日期且相差 >7 天即判不同事件、`composite_score` 返回 0；`_close_date` 改用新字段，`_date_proximity` 据真实日期计算。**仅当双方都有日期时才比较**(任一未知按中性处理),因日期 veto 只阻止匹配(错配→真亏钱)、不制造匹配(漏配→只是错过),缺数据时不误拒,符合「宁可漏不可错」。
  - 真实数据端到端验证:外星人正确一对(均 2026-12-31、标题一致)匹配 1.000,所有错误日期子市场被 veto 到 0.000。新增测试 16 个(日期 veto 8 + 适配器解析 8)，全套 **634 个测试通过**。

- **套利配置闸门（后端防虚假套利 · 真实数据驱动）**：`ArbitrageEngine` 新增两个可配置闸门，在源头过滤掉「7 Fed rate cuts」那类假套利：
  - `max_implied_prob_divergence`（默认 0.10）：同一事件两平台隐含 P(YES) 背离超过此值即跳过——大背离=一侧定价脏/薄/结算口径不同，非真套利（Fed cuts: Polymarket 0.4% vs predictfun 17.6%/49%）。
  - `min_recommended_size_usd`（默认 20）：可成交规模（受最薄腿流动性限制）低于此值即跳过——薄盘利润易被链上 gas 吃掉。
  - `config.py`/`config.yaml` 加配置项并默认启用；`app.py` 接入。真实验证：启用后 Fed cuts 假单从机会列表消失。新增测试 5 个。
- **套利信号实时性（F-2：已匹配市场固定抓取）**：`PredictFunAdapter` 新增 `pinned_ids`——已匹配（在某个等价组里）的市场即使因成交量下滑跌出 top-N，也会按 `/v1/markets/{id}` 单独抓取并合入，避免已建立的跨平台套利对忽隐忽现。`run_pipeline_once` 每周期把匹配组成员 ID 反馈给适配器（解包 ResilientAdapter）。新增测试 2 个。
- **UI 重设计（参考 matchr.xyz）+ 套利可靠性分析**：`dashboard.html` 重做为「机会卡为主角 + 标签页导航」终端风格——顶部统计条、机会卡并排展示两平台（美分计价）、匹配置信度徽章、诚实免责声明；机会卡显示两平台隐含 P(YES)，背离 >10% 红色警告，小规模提示 gas 风险。
- 更新 `docs/13`：补充缺口 D-2/D-3/F-2 与「7 Fed cuts」案例复盘。全套 **616 个测试通过**。

### 修复
- **「夺冠 vs 赢小组」虚假套利（真实数据发现的匹配错误 · 高 · 资金安全）**：用户在仪表盘发现持续存在的 122% "Will Mexico win the 2026 FIFA World Cup?" 套利。排查发现两个市场**根本不是同一事件**：Polymarket 是「夺得世界杯冠军」(墨西哥 1.4%)，predict.fun 是「赢得 A 组」(墨西哥 56%)——标题仅差「Group A in」，复合相似度 0.864（>0.85 阈值）被误判等价。修复：`matching.py` 新增**赛段/范围限定词硬 veto** `_scope_signature`/`_scope_mismatch`（小组赛及组别、淘汰赛轮次 ro16/ro32/quarterfinal/semifinal、advance/qualify），签名不一致即判不同事件、`composite_score` 返回 0（保护 cross_ref 与普通评分两条路径）。真实服务验证：Mexico 虚假套利消失，套利机会 3→0、匹配组 55→15。

### 修复（用户反馈）
- **模拟盘确认后持仓不变**：默认 `dry_run: true` 下，`execute_plan` 走演练分支、完全不触达适配器，导致在仪表盘确认计划后**模拟盘持仓/收益毫无变化**，看起来像没成交。根因是 dry-run 把「模拟盘」也一并跳过了，而模拟盘本就不动真钱、dry-run 对它无意义。修复：给 `PaperExecutionAdapter` 加 `is_paper=True` 标识；`execute_plan` 改为 **dry-run 只抑制真实（会动真钱）适配器，模拟盘始终照常模拟成交**（持仓、余额、已实现收益都更新）。这样默认配置下也能看到模拟交易效果，而真实适配器接入后 `dry_run: true` 仍正确抑制真实下单。端到端验证：确认计划后两腿等量建仓、已实现收益正确核算。更新/新增相关测试。

### 新增
- **模拟盘真实成交 + 每笔交易真实收益核算（Phase 3 · 切片 H/I · 任务 2）**：非 dry-run 模式下确认计划会经模拟盘**真实建仓**（等量对冲合约、更新持仓），并按**实际成交价**核算已实现收益——`TradePlan` 新增 `filled_cost_usd`/`expected_payoff_usd`/`realized_profit_usd`/`realized_profit_margin` 与 `is_genuinely_profitable`。核算逻辑：对冲赔付 = 各腿成交量最小值 × $1，成本 = Σ(成交量×成交均价)，收益 = 赔付 − 成本。**关键价值**：检测时为正的套利，若因滑点/费用按实际成交价不再盈利，会被标记「✗ 实亏」（已加滑点亏损测试）。`ExecutionEngine.last_orders` 暴露已成交订单供持久化对账（修复此前 `_find_order` 占位缺口）。新增 API `GET /trade/pnl`（盈亏汇总），`TradePlanResponse` 增真实收益字段，仪表盘交易计划卡显示每笔「真盈利/实亏」与累计盈亏。端到端验证：$85 预算 → 双腿各 100 合约 → 成本 $85、赔付 $100、已实现收益 $15（17.65%）。新增测试 10 个。

### 修复（功能审计驱动 · 健壮性与资金安全）
- **双腿资金/合约数错误（高 · 资金安全）**：`ExecutionEngine.build_plan` 此前每腿按 `size_usd/腿价` 独立折算，导致 (a) 实际部署约 2×预算、与风控核准不符，(b) 两腿合约数不等、根本不构成对冲。修复为套利应买**等量合约** `N = size_usd / 每对成本`，各腿同 N，总投入=预算。实测：$100 预算 → 两腿各 117.65 合约、总投入精确 $100。
- **敞口上限形同虚设（高 · 资金安全）**：流水线 `propose(listed)` 不传敞口，总/单市场敞口上限恒按"零已用"计算、从不生效。修复：`TradingService` 自核算未终结/已完成计划的总敞口与各市场敞口（`_current_exposure`），并在同一周期内累计新计划敞口，使总/单市场上限真正约束核准规模。新增敞口绑定测试（4 个）。
- **ask≈0 产生虚假套利（高）**：`ArbitrageEngine` 此前 ask=0（脏数据/无报价）会算出 `(1-≈0)/≈0` 的虚假超高利润率。修复：新增 `MIN_TRADEABLE_ASK=0.001`，ask≤该值视为不可定价的数据缺陷而跳过该腿。新增测试（2 个）。
- **告警重试耗尽后永久丢失（中）**：`AlertService` 此前投递前即标记已告警，全部重试失败的机会在"清除并重现"前再也收不到告警。修复：仅投递成功（至少一个通道）才标记，失败的机会下周期重试；`_deliver` 返回成功与否。更新告警测试。
- **SQLite 连接泄漏（中）**：`stop_background` 此前只取消任务、不关闭 DB 连接。修复：停机时关闭 signal/history/trade 三个 store 的 SQLite 连接。
- **信号事件流无限增长（中）**：`InMemorySignalStore`（默认保留 5 万条）与 `SqliteSignalStore`（默认保留 20 万条，每 500 次追加机会性裁剪）加保留上限，防长跑进程内存/磁盘无限增长。

### 修复（数据实时性/稳定性审计驱动 · 关键）

  - `observability.py`（新模块）：`JsonLogFormatter`（单行 JSON 日志）、`configure_json_logging(level)`（幂等地把根日志切为 JSON）、`PipelineMetrics`（累计 `cycles_total` / `signals_opened_total` / `signals_closed_total` / `alerts_fired_total` 与最近周期 `last_*` 快照，`snapshot()` 可 JSON 序列化）。
  - `synonyms.py`（新模块）：`DEFAULT_SYNONYM_GROUPS` 同义词/缩写词典 + `SynonymNormalizer`（`normalize` / `normalize_all`），把 `btc→bitcoin`、`potus→president`、`over→above` 等归一到规范词。
  - `matching.py`：新增三个相似度后端——`EmbeddingSimilarity`（注入式编码器，余弦映射到 [0,1]）、`HybridSimilarity`（词法 + 语义加权融合）、`NormalizingLexicalSimilarity`（词法 + 同义词归一，默认增强）；均零外部依赖。
  - `api.py`：新增 `GET /metrics` 端点（未配置时返回 `{}`，否则返回 `PipelineMetrics.snapshot()`）。
  - `app.py`：`run_pipeline_once` 末尾 `record_cycle`；`build_application` 按 `json_logging` 启用 JSON 日志、按 `similarity_backend` 选择匹配相似度后端。
  - `config.py`：`ScannerSettings` 新增 `json_logging`（默认 `false`）与 `similarity_backend`（默认 `"lexical"`，可选 `"normalizing"`）。
  - 新增测试 `test_matching_semantic.py`（信号质量，本轮新增 23 个），扩展 `test_pipeline.py`（metrics 埋点端到端）；可观测性 `test_observability.py` / `test_api_metrics.py`（16 个）此前已纳入。全套 **388 个测试通过**（原 365 + 新增 23）。

- **数据接入健壮性（Phase Two · 切片 C）**：保证信号基于真实、稳定的数据。
  - `resilience.py`（新模块）：`RateLimiter`（最小间隔限流）、`Retry`（指数退避重试）、`CircuitBreaker`（连续失败熔断 + 半开探测恢复）、`AdapterMetrics`，以及把三者组合的 `ResilientAdapter` 包装器——核心与适配器零改动。
  - `config.py`：新增 `adapter_min_interval_seconds` / `adapter_max_attempts` / `adapter_backoff_base_seconds` / `circuit_failure_threshold` / `circuit_reset_timeout_seconds`。
  - `app.py`：从配置构造的适配器统一用 `ResilientAdapter` 包装；`/health` 经 health_provider 汇报熔断状态与成功/失败计数。
  - `api.py`：`AdapterHealth` 新增 `circuit_state` / `success_count` / `failure_count` 字段。
  - 新增 Property 15（限流间隔）、16（退避上限）、17（熔断状态机）；新增测试 `test_resilience.py`（23 个）；全套 **349 个测试通过**（原 326 + 23）。

- **信号持久化（Phase Two · 切片 B）**：信号与事件流可跨重启不丢、可审计。
  - `signals.py`：新增 `SqliteSignalStore`（标准库 `sqlite3`，零外部依赖），实现 `SignalStore` 接口；`active_signals` + `signal_events` 两表，pydantic JSON 序列化；重启自动恢复活跃信号，无需额外代码。
  - `config.py`：`ScannerSettings` 新增 `signal_store_path`（None=内存，路径=SQLite）。
  - `app.py`：`build_application` 按配置选择内存或 SQLite 存储。
  - 新增测试 `test_signals_sqlite.py`（含重启恢复、事件保序、upsert 幂等）+ 配置测试；全套 **326 个测试通过**（原 309 + 17）。

- **信号生命周期（Phase Two · 切片 A）**：将无状态的瞬时机会提升为有状态的 `Signal`，建立 `OPEN → SUSTAINED → CLOSED` 生命周期。
  - `models.py`：新增 `SignalStatus`、`SignalEventType`、`Signal`（含 `duration_seconds`、`peak_net_profit_margin`、生命周期时间戳）、`SignalEvent`。
  - `signals.py`（新模块）：`SignalStore` 接口 + `InMemorySignalStore` 内存实现 + `SignalService.reconcile()`，每周期对账信号状态并产出事件流。
  - `app.py`：流水线在机会对账后接入信号对账。
  - `api.py`：新增 `GET /signals`（活跃信号，按净利润率降序）与 `GET /signals/events`（事件流，支持 `limit`）。
  - 新增正确性属性 Property 13（信号状态一致性）、Property 14（事件与状态一致）。
  - 新增测试 `test_signals.py`、`test_api_signals.py`，扩展 `test_pipeline.py`；全套 **309 个测试通过**（原 295 + 14）。

## [0.1.0] - 2026-06-08

第一阶段（Phase One）完成：实时检测与呈现跨平台预测市场套利机会。

### 新增
- 规范数据模型（`Outcome` / `CanonicalMarket` / `EquivalentMarketGroup` / `ArbitrageOpportunity` 等），含价格界限、非负量、置信度等校验。
- 存储层：`MarketStore`（Protocol + 内存实现）与 `OpportunityStore`。
- 平台适配器边界 `PlatformAdapter` 与统一错误 `AdapterError`；可复用一致性测试套件。
- 费用模型 `FlatFeeModel`（Polymarket）与非线性 `KalshiFeeModel`。
- `PolymarketAdapter`（Gamma + CLOB）与 `KalshiAdapter`（trade-api v2，分→概率，密钥鉴权）。
- `IngestionService`：每适配器一个异步刷新循环、故障隔离、时间戳、过期标记，支持注入时钟。
- `RankingService`：按交易量/流动性排序与阈值过滤。
- `MatchingEngine`：分块候选生成 + 复合相似度评分 + 结果映射（含反转），`SemanticSimilarity` 接口与词法默认实现。
- `ArbitrageEngine`：基于 ask 价、计入费用与价差的净利润率计算，按流动性限规模，过期/低置信度组排除。
- `OpportunityService`：机会过滤（去 ≤0 与低于阈值）、排序、失效移除。
- `AlertService`：`AlertCriteria` 匹配，`LogChannel` / `WebhookChannel`，失败重试（≤3）与去重。
- `ConfigLoader`：YAML 配置，启用/禁用平台、缺密钥优雅降级、默认 60s 过期阈值可覆盖。
- 读取 API（FastAPI）：`/markets`、`/groups`、`/opportunities`、`/health`、`GET/PUT /config/alerts`，响应含新鲜度字段。
- `ScannerApplication` 组合根与 `uvicorn` 入口，端到端流水线接线与周期执行。
- 示例 `config.yaml`、录制 JSON fixtures、README 运行说明。
