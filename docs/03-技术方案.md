# 03 · 技术方案

本文档说明技术选型理由、三个核心算法（匹配 / 套利 / 费用）的实现细节，以及关键工程决策。

## 1. 技术选型

| 关注点 | 选择 | 理由 |
|---|---|---|
| 语言 / 运行时 | Python（目标 3.11+，当前开发环境 3.9） | 并发网络 I/O 友好，数据生态强，与平台工具链一致 |
| HTTP 客户端 | `httpx`（异步） | 异步 REST 轮询，支持超时与连接池 |
| WebSocket | `websockets` | 平台支持时的实时价格流（预留） |
| API 层 | `FastAPI` + `uvicorn` | 类型化请求/响应、异步、自带 OpenAPI |
| 数据模型 | `pydantic` v2 | 边界处校验价格区间、非负量 |
| 进程内存储 | 内存 dict（接口化） | 第一阶段实时快照；接口允许后续换持久化 |
| 调度 | `asyncio` 任务 + 间隔循环 | 每适配器一个刷新循环，无需外部调度器 |
| 配置 | `PyYAML` | YAML 配置文件 |
| 测试 | `pytest` + `pytest-asyncio` + `respx` | 确定性单测，mock httpx 网络 |

> **Python 版本说明**：设计目标为 3.11+，但当前开发机仅有 3.9.6。代码全程使用 `from __future__ import annotations` 与 3.9 兼容的类型写法，向前兼容 3.11+，无需改动。

## 2. 规范数据模型

所有平台数据被规范化为 `CanonicalMarket`（`scanner/models.py`），核心字段：

```python
class Outcome(BaseModel):
    name: str                       # 规范化为 "YES" / "NO"
    price: float                    # 隐含概率 0..1
    bid: float | None               # 最优买价（价差成本用）
    ask: float | None               # 最优卖价
    available_liquidity_usd: float | None

class CanonicalMarket(BaseModel):
    platform: str                   # "polymarket" | "kalshi"
    market_id: str
    title: str
    outcomes: list[Outcome]
    volume_usd: float | None
    liquidity_usd: float | None
    fee_rate: float | None
    retrieved_at: datetime          # UTC
    field_status: dict[str, FieldStatus]   # 每字段可用性
    unavailable_reasons: dict[str, str]
    is_stale: bool = False
    # age_seconds 为计算属性
```

`pydantic` 校验器强制：价格/bid/ask ∈ [0,1]（Property 1）、volume/liquidity 为 None 或 ≥0（Property 2）、match_confidence ∈ [0,1]（Property 7）。

适配器负责把原生数据转成规范形式：Kalshi 分→概率（÷100）、各平台量值→美元。缺失字段标记 `FieldStatus.UNAVAILABLE` 并记录原因。

## 3. 核心算法一：跨平台匹配（MatchingEngine）

匹配是最大的技术风险，采用**分层、可解释**的流程，而非黑盒模型。

### 3.1 分块 / 候选生成（Blocking）

将 O(N²) 的成对比较缩减为只比较「可能匹配」的对：

- 从标题提取**实体词**（数字、年份、阈值、去除停用词后的关键词）作为分块键。
- 只有**共享至少一个分块键**且**来自不同平台**的市场对才进入下一步。
- 支持可选的额外提取器（类别、收盘日期）。

效果：两个表述不同但讲同一件事的市场（"Bitcoin above 100000 in 2025" vs "Bitcoin above 100000 by 2025"）会因共享 `bitcoin`、`100000`、`2025` 落入同一块。

### 3.2 复合相似度评分

对每个候选对计算加权复合分（权重见 `ScoreWeights`，归一化后和为 1）：

| 信号 | 默认权重 | 说明 |
|---|---|---|
| 标题语义相似度 | 0.50 | 通过 `SemanticSimilarity` 接口，默认词法实现（token-set ratio + Jaccard） |
| 实体重叠 | 0.25 | 两标题实体词的 Jaccard 重叠 |
| 结构兼容 | 0.15 | 双方都是二元 YES/NO 则为 1 |
| 日期接近 | 0.10 | 收盘日期接近程度（无日期时中性 0.5） |

复合分即 `match_confidence ∈ [0,1]`。

### 3.3 结果映射与排除

- 对齐结果：YES↔YES、NO↔NO；当一个平台把问题表述为否定（标题含 not/won't 等）时记为**反转（inverted）**。
- **若某市场的任一结果无法映射**（如三元市场、无法识别极性），该市场被排除出组（Property 6）。

### 3.4 可升级性

`SemanticSimilarity` 是接口，默认 `LexicalSimilarity` 无外部依赖、可离线运行。未来可替换为嵌入模型（embedding cosine）而不动其余逻辑。

## 4. 核心算法二：套利检测（ArbitrageEngine）

对一个跨平台匹配的二元市场组：

```
# 为每个规范结果选取「最低 ask」的平台
cost_per_pair   = Σ(每个规范结果的最低 ask)        # 例如 ask_YES(A) + ask_NO(B)
gross_margin    = (1 - cost_per_pair) / cost_per_pair
fees_per_pair   = Σ(各选中腿的 feeModel.fee_for(ask, 1))
net_cost        = cost_per_pair + fees_per_pair
net_margin      = (1 - net_cost) / net_cost          # 净利润率
recommended_size_usd = 最薄一腿的可用流动性          # 受流动性限制
```

要点：

- **用 ask 价**（跨越价差的真实成本），不用中间价（需求 5.2）。
- **只评估非过期组**（`is_stale=False` 且未超过 `staleness_threshold`，Property 5）。
- **只评估达到置信度阈值的组**（`match_confidence >= match_confidence_min`，Property 7）。
- **记录每个被评估组的机会，包括 ≤0 的利润率**（需求 5.3）；过滤/移除由 `OpportunityService` 负责。
- `net_margin <= gross_margin` 恒成立，因费用非负（Property 8）。
- 建议规模不超过最薄一腿流动性（Property 9）；流动性不可用时按 0 处理。
- 通过「逐结果选最低 ask」泛化到 N 个平台成员。

## 5. 核心算法三：费用模型（FeeModel）

费用逻辑独立于套利引擎，按平台选择：

```python
class FeeModel(Protocol):
    def fee_for(self, price: float, contracts: float) -> float: ...

class FlatFeeModel:    # Polymarket 风格，第一阶段 rate=0.0
    # fee = rate * price * contracts
    ...

class KalshiFeeModel:  # Kalshi 非线性费用
    # fee = ceil(0.07 * contracts * price * (1-price) * 100) / 100  （向上取整到分）
    ...
```

- Kalshi 费用在 `price=0.5` 时最大，在价格极值（0 或 1）时归零。
- 系数可配置以适配不同 Kalshi 费率档。

## 6. 摄取与故障隔离

- 每个启用的适配器一个 `asyncio` 循环，间隔 `refresh_interval`（≤60s，需求 1.3）。
- 每次适配器调用包裹在 `asyncio.wait_for(timeout=fetch_timeout)` 中。
- 超时 / `AdapterError` / 任意异常都被捕获并以适配器名记录日志，**保留上一份正常数据，继续其他适配器**（Property 4）。
- 成功时打 `retrieved_at`；每周期重算 `is_stale = age_seconds > staleness_threshold`（Property 5）。
- **可注入时钟**：构造时传入 `clock` 回调，使时间戳与过期判定在测试中确定可控。

## 7. 告警的重试与去重

- 满足 `AlertCriteria` 的**新**机会触发告警，载荷含事件、平台、净利润率、检测时间（需求 6.3）。
- 失败通道带指数退避重试，**每个机会每通道至多 3 次**（Property 11）；退避 `sleep` 可注入，便于测试。
- **去重**：记录已告警的 group_id；机会消失后清除其状态，使其重新出现时可再次告警（「清除前不重复告警」）。
- 一个失败通道不阻塞其他通道。

## 8. 配置驱动的可扩展性

- 适配器按名称从配置加载（需求 7.1）；`app.py` 中的 `ADAPTER_FACTORIES` 把平台名映射到构造函数。
- 新增平台 = 实现一个适配器 + 在工厂表注册一行，核心零改动（需求 7.2）。
- 被禁用的平台、或缺少必需 API 密钥的平台（如 Kalshi 缺 `KALSHI_API_KEY`）被完全排除，且只排除该适配器，其他继续（Property 12）。

## 9. 关键工程决策小结

| 决策 | 取舍 |
|---|---|
| 内存存储 | 第一阶段足够、零运维；接口化保留替换空间 |
| 词法相似度做默认 | 可离线、确定性、零外部依赖；牺牲部分语义精度，留接口待升级 |
| 注入时钟与网络 | 测试完全确定、离线；少量构造样板代码 |
| 只读 API + 无鉴权 | 第一阶段简单；生产需在前置加鉴权网关（见 [07](./07-部署与运维.md)） |
