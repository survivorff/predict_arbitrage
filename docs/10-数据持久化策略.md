# 10 · 数据持久化策略

本文说明系统各类数据**存在哪里、用什么策略、重启后是否保留**。核心原则：**瞬时数据放内存、有价值的历史落盘**。

## 总览

| 数据类型 | API 端点 | 存储位置 | 策略 | 重启后 |
|---|---|---|---|---|
| 市场行情 | `/markets` | **内存**（`InMemoryMarketStore`） | 实时快照，每个摄取周期覆盖刷新 | 丢失，重新拉取 |
| 等价市场组 | `/groups` | **内存**（每次请求/周期重算） | 由当前行情即时计算，不落盘 | 丢失，重新计算 |
| 套利机会 | `/opportunities` | **内存**（`OpportunityStore`） | 每周期重算的瞬时快照 | 丢失，重新计算 |
| **信号 + 事件流** | `/signals`、`/signals/events` | **SQLite 文件**（`signals.db`） | 活跃信号 upsert、事件流只追加 | **保留**，可审计 |
| 运行指标 | `/metrics` | **内存**（`PipelineMetrics`） | 进程内累计 + 最近周期快照 | 归零 |
| **行情/机会历史** | `/opportunities/{gid}/history`、`/markets/{platform}/{id}/history` | **SQLite 文件**（`history.db`） | 每周期写净利润率/YES 价采样点，按保留窗口（默认 7 天）裁剪 | **保留** |
| 订单 / 交易计划 | `/trade/plans`（交易 API） | **SQLite**（`trades.db`，`TradeStore`） | upsert 持久化，可对账；计划状态机 待确认→确认→执行→完成/失败/拒绝 | **保留** |
| 告警去重状态 | — | **内存**（`AlertService`） | 进程内记录已告警 group | 重置 |

## 为什么这样设计

- **行情 / 机会是瞬时的**：价格几秒就变，存历史快照既占空间、时效性又低。它们随时能从平台 API 重新拉取，因此放内存、每周期覆盖刷新即可。
- **信号是有状态、有价值的历史**：一个套利信号「何时出现、持续多久、峰值多少、何时消失」是值得长期保留与审计的——这是「信号捕捉工具」的核心产物，因此落 SQLite，跨重启恢复活跃信号、事件流只追加可回放。
- **接口化存储**：`MarketStore` / `SignalStore` / `TradeStore` 都是 Protocol，内存与 SQLite 实现可互换；未来要换 Redis/Postgres 不动调用方。

## 信号持久化细节（`signals.db`）

- 位置：项目根目录 `signals.db`（由 `config.yaml` 的 `scanner.signal_store_path` 指定；留空则用内存、重启丢失）。
- 两张表：
  - `active_signals`：当前活跃信号，以 `group_id` 为主键，整条信号以 pydantic `model_dump_json()` 存于 `payload` 列；信号关闭即删行。
  - `signal_events`：事件流，只追加，自增 `id` 保证回放顺序（OPENED / UPDATED / CLOSED）。
- 重启恢复**无需额外代码**：活跃信号天然在表中，新进程打开同一文件即恢复。
- 写操作即时 `commit`，进程崩溃后仍可恢复。

## 行情/机会历史持久化细节（`history.db`）

- 位置：项目根目录 `history.db`（由 `config.yaml` 的 `scanner.history_store_path` 指定；留空则用 `NullHistoryStore`、不记录历史）。保留窗口由 `scanner.history_retention_days` 配置（默认 7 天）。
- 两张表（每周期每组/每市场一行，很轻量）：
  - `opportunity_history`：`group_id` / `label` / `margin`（净利润率）/ `ts` —— 画机会的价差/利润率走势。
  - `market_price_history`：`platform` / `market_id` / `label` / `price`（YES 价）/ `ts` —— 回看价格变动。
- **保留策略**：写入机会时机会性删除超出保留窗口的旧行（`ts < now - retention_days`），控制库膨胀。查询按时间升序返回，便于直接画图。
- 用途：仪表盘机会行点开展开净利润率走势迷你图（调 `/opportunities/{gid}/history`）；信号触发时的价差回看。
- 接口化（`HistoryStore` Protocol），将来可换时序库（TimescaleDB / InfluxDB）不动调用方。

## 已知缺口（视需求决定是否补）

- **历史采样粒度为「每检测周期一点」**：当前不存完整盘口快照（仅净利润率与 YES 价），如需「某时刻两平台完整订单簿回看」需扩展表结构。
- **指标不持久**：`/metrics` 的累计量重启归零。若要长期监控趋势，建议接入 Prometheus（见迭代计划横向改进）。

## 运维提醒

- `signals.db`、`trades.db`、`history.db`、`*.db` 已在 `.gitignore` 中忽略，不会误提交。
- 备份历史：直接复制 `signals.db` / `history.db` 文件即可（SQLite 单文件）。
- 清空历史：停服务后删除对应 `.db` 文件，重启会重建空库。
- 历史库膨胀受 `history_retention_days` 控制；可按需调小保留窗口。
