# 11 · 真实下单交易测试准备清单

> ⚠️ 本文件是「从模拟盘走向真实资金下单」的准备清单与风险须知。**当前系统默认 dry-run（演练，不动真钱）**，真实下单是质的跨越，需逐项准备就绪并经人工确认后才推进。本文件只列准备事项，不含任何密钥/私钥（密钥只经环境变量注入，绝不入库）。

## 1. 现状：已就绪 vs 缺口

### ✅ 已就绪（不涉及真实资金）
- **检测链路**：行情摄取 → 跨平台匹配 → 套利检测 → 信号生命周期，全部跑通（双平台真实数据）。
- **风控闸门**（切片 G）：单笔/单市场/总敞口上限、滑点保护、信号新鲜度、最小净利润率、余额校验，逐条可解释。
- **半自动确认流**（切片 H）：机会 → 风控 → 待确认计划 → 人工确认/拒绝 → 执行；交易 API + 仪表盘操作；交易 API 鉴权（`X-API-Key`）。
- **执行引擎**（切片 F）：双腿原子性、一腿失败补救、残余敞口检测、订单/计划持久化。
- **模拟盘执行适配器** `PaperExecutionAdapter`：全链路打通，但**不连真实平台、不动真钱**。
- **dry-run 安全开关**：`execute_plan(dry_run=True)` 只演练不下单。
- **钱包只读接入**（切片 M）：浏览器插件钱包连接、看地址/余额，私钥不离浏览器。

### ❌ 缺口（真实下单的硬前置，尚未实现）
- **真实执行适配器**（切片 I）：对接 Polymarket CLOB / predict.fun 的真实下单 API（含 EIP-712 签名、JWT 鉴权）。当前执行侧只有模拟盘，**从未连过真实交易 API**。
- **前端真实签名下单**（切片 N）：浏览器钱包对订单做 EIP-712 签名后提交平台。
- **真实 API 只读连通验证**：用真实账户读余额/持仓（验证凭证与数据通路）——这是最稳妥的第一步。

## 2. 需要你准备的东西

### 2.1 账户与身份
- [ ] **Polymarket 账户**：一个有资金的钱包地址（Polygon 链）。Polymarket 用 CLOB，需要：
  - 钱包（如 MetaMask）私钥/助记词 —— **只你自己掌握，绝不发给任何人或写入代码**。
  - 账户已在 Polymarket 完成入金（USDC on Polygon）。
- [ ] **predict.fun 账户**：BNB Chain 上的钱包地址。需要：
  - 钱包私钥/助记词（同样只你掌握）。
  - 账户已入金（predict.fun 的结算币种）。
  - 已有的 API key（你已申请：通过环境变量 `PREDICTFUN_API_KEY` 使用）。
- [ ] 确认两个账户**实名/合规**状态满足平台要求（部分地区受限）。

### 2.2 资金
- [ ] **小额验证资金**：建议每个平台先放**极小额**（如等值 $10–$50）用于首次真实下单验证。
- [ ] 明确**单笔上限**与**总敞口上限**（写入 `config.yaml` 的 `risk:` 段，当前默认单笔 $100 / 总 $1000，首次验证应调更小，如单笔 $5）。
- [ ] 预留**两个平台各自的 gas/手续费**（链上交易需要原生币：Polygon 需 POL、BNB Chain 需 BNB）。

### 2.3 链上与签名
- [ ] 两条链的钱包都已添加并能正常签名（Polygon、BNB Chain）。
- [ ] 理解**EIP-712 签名**流程：真实下单时订单由钱包签名，**私钥不离浏览器/本地**，服务器只做编排与记录。
- [ ] predict.fun 下单流程：取 auth message → 钱包签名换 JWT → 签订单提交。
- [ ] Polymarket 下单流程：CLOB 订单签名（EIP-712）→ 提交 CLOB API。

### 2.4 环境与配置
- [ ] 环境变量（绝不写入文件）：
  - `PREDICTFUN_API_KEY`（已有）
  - 真实下单的钱包凭证如何注入（建议用浏览器钱包签名，服务器**不持有私钥**；若用服务端签名方案则需 `*_PRIVATE_KEY` 环境变量，风险更高，不推荐）。
  - `SCANNER_TRADE_API_KEY`（交易 API 鉴权，真实下单前务必启用并在 `config.yaml` 设 `trade_api_key_env`）。
- [ ] `config.yaml` 调整：
  - `risk.dry_run: false`（**仅在全部验证通过后**才改）。
  - `risk.max_trade_size_usd` 调到首次验证的极小额。
  - `risk.require_confirmation: true`（保持人工确认）。

### 2.5 风险确认（务必理解）
- [ ] **双腿原子性风险**：套利需两腿都成交；若一腿成交、另一腿失败 → 单边裸敞口，可能亏损。引擎有补救（反向平掉已成交腿），但补救也可能失败（残余敞口需人工介入）。
- [ ] **滑点风险**：真实成交价可能偏离信号价；风控有滑点保护，但极端行情仍可能不利成交。
- [ ] **资金损失风险**：任何 bug 或市场异动都可能导致真实亏损。首次务必极小额。
- [ ] **不可逆性**：链上交易一旦提交不可撤销。
- [ ] **kill switch**：需要一个紧急停机开关（一键停止所有下单）—— 待切片 J 落地，真实下单前应具备。

## 3. 建议的推进顺序（稳妥路线）

1. **第一步：真实 API 只读连通验证**（最安全，不下单不动钱）
   - 实现真实执行适配器的「读」部分：连真实平台读账户余额、持仓。
   - 验证凭证有效、数据通路正确。此前执行侧全是 mock，从未连过真实平台。
2. **第二步：dry-run 全链路真实数据演练**
   - 用真实行情 + 真实账户余额跑「机会 → 风控 → 待确认 → 确认 → dry-run 执行」，核对「将要下的单」的价格/数量/费用与真实账户状态一致。
3. **第三步：受控小额真实下单（单平台、单腿先行）**
   - 极小额、人工逐笔监督，先验证单腿真实成交与回报、持仓跟踪正确。
4. **第四步：小额双腿套利真实验证**
   - 真实跑通双腿原子性，重点验证一腿失败时的补救路径。
5. **第五步：生产加固（切片 J）**
   - kill switch、故障演练、对账流程、上线检查清单。

## 4. 安全红线（贯穿全程）
- 默认 dry-run；真实下单必须显式开启 + 人工确认。
- 私钥/助记词只你掌握，绝不入代码、日志、API 响应、git。
- 真实下单前必须先通过真实 API 只读连通验证。
- 任何时候不放任单边裸敞口；双腿失败必须有补救与告警。
- 提供紧急停机开关（kill switch）。
- 首次真实下单用极小额，人工逐笔监督。

## 5. 一句话总结
**软件侧的检测、风控、确认流、执行引擎、模拟盘都已就绪；真实下单还差「真实执行适配器 + 真实账户凭证 + 小额资金 + 你的明确授权」。** 最稳妥的下一步是先做「真实 API 只读连通验证」（读余额/持仓，不下单）。
