## 3. 已知限制与技术债

| 项 | 说明 | 影响 | 优先级 |
|---|---|---|---|
| 内存存储 | 重启丢失快照，无历史 | 不支持跨重启、无回溯 | 中 |
| 词法相似度 | 默认匹配为词法，非语义嵌入 | 措辞差异大的等价市场可能漏匹配 | 高 |
| 无鉴权 API | 只读但无访问控制 | 生产需前置网关 | 高（部署前） |
| 仅二元市场 | 当前聚焦 YES/NO | 多结果市场未覆盖 | 中 |
| 告警配置不持久 | PUT `/config/alerts` 仅内存 | 重启失效 | 低 |
| Polymarket 费率固定 0 | 未动态读取真实费率 | 个别市场利润率略偏乐观 | 低 |
| 无指标/监控埋点 | 仅日志 | 生产可观测性有限 | 中 |

## 4. 第二阶段（✅ 已完成）：生产级信号捕捉

**目标**：把第一阶段的「瞬时扫描器」升级为**生产级套利信号捕捉工具**——信号真实、可信、不丢失、可追溯。

> 设计取向：聚焦「信号捕捉」核心，不做交易执行、不做花哨 UI。一切以「信号的可信度与完整性」为最高优先级。

> 📌 Phase Two 四个切片（A 信号生命周期 / B 信号持久化 / C 数据接入健壮性 / D 信号质量与可观测性）**已全部完成**。

### 切片划分（按优先级与依赖排序）

围绕「一个套利信号从产生到消失的完整生命周期」来组织，分为 4 个可独立交付、可测试的切片：

#### 切片 A：信号生命周期与事件模型（✅ 已完成 · 内存版）
将「机会（Opportunity）」提升为有状态的「信号（Signal）」，建立完整生命周期与事件流。

- [x] 定义 `Signal` 模型与状态机：`OPEN`（首次检测）→ `SUSTAINED`（持续存在）→ `CLOSED`（价差消失/失效），记录 `first_detected_at`、`last_seen_at`、`closed_at`、峰值净利润率、持续时长。
- [x] 定义 `SignalEvent` 事件流（OPENED / UPDATED / CLOSED），作为信号工具的核心产物——可被消费、回放、审计。
- [x] `SignalService`：在每个流水线周期对账，由机会快照驱动信号状态转移并产出事件。
- [x] API 增补：`GET /signals`（当前活跃信号 + 状态/持续时长）、`GET /signals/events`（事件流）。
- [x] 单元 + 集成测试：信号开启/持续/关闭的状态转移、峰值与时长记录、事件产出顺序；新增正确性属性 Property 13/14。

> 当前为**内存实现**（`InMemorySignalStore`）。`SignalStore` 接口已就绪，切片 B 将无缝叠加 SQLite 持久化。

#### 切片 B：信号持久化（✅ 已完成 · SQLite）
- [x] 定义 `SignalStore` 接口（与现有存储一致的接口化风格）。
- [x] 提供 SQLite 实现（零外部依赖、可文件落盘），持久化信号与事件流；接口预留 Postgres。
- [x] 启动时恢复活跃信号快照；事件流持久追加（支持回放/审计）。
- [x] 测试：重启恢复、事件持久顺序、并发 upsert 幂等。

> 由配置 `scanner.signal_store_path` 开关：`None`→内存（重启丢失）；文件路径→SQLite 持久化。重启恢复无需额外代码——活跃信号天然在表中。

#### 切片 C：数据接入健壮性（✅ 已完成）
- [x] 适配器层加入**限流**（最小请求间隔）与**指数退避重试**，遵守平台 API 速率限制。
- [x] **熔断器**：连续失败的平台短暂熔断，避免雪崩；半开探测恢复，并反映到 `/health`。
- [x] 抓取指标（成功/失败/限流/熔断拒绝/熔断状态）暴露到健康端点。
- [x] 测试：限流节流、退避次数、熔断开合状态机（注入时钟，确定性）。

> 通过 `ResilientAdapter` 包装实现，核心与适配器零改动。开关见配置 `scanner.adapter_*` / `scanner.circuit_*`。新增 Property 15/16/17。

#### 切片 D：信号质量与可观测性（✅ 已完成）
- [x] 引入可插拔的语义相似度后端（实现 `SemanticSimilarity`），提升等价市场召回、减少漏信号；词法实现保留为离线兜底。
- [x] 结构化日志（JSON）+ 关键指标埋点（信号开启率、平均持续时长、各阶段耗时），便于生产诊断。
- [ ] 告警配置持久化（随 `SignalStore`）。
- [x] 测试：语义后端的召回对比、指标埋点正确性。

> 实现要点：
> - **可观测性**：`observability.py` 提供 JSON 日志（`JsonLogFormatter` + 幂等的 `configure_json_logging`）与 `PipelineMetrics`（累计 + 最近快照），经新增的 `GET /metrics` 端点暴露；由配置 `json_logging` 开关。
> - **信号质量**：`synonyms.py` 的 `SynonymNormalizer` + `NormalizingLexicalSimilarity` 作为默认词法的「即插即用」增强（由配置 `similarity_backend` 选择）；`EmbeddingSimilarity` / `HybridSimilarity` 提供可插拔语义后端，三者均零外部依赖。实测：措辞不同的等价市场（BTC vs Bitcoin、over vs above、POTUS vs Presidential）相似度从约 0.61/0.735 提升到约 1.0，无关标题仍 <0.3。
> - 新增测试 `test_matching_semantic.py`（信号质量，本轮新增 23 个）；可观测性 `test_observability.py` / `test_api_metrics.py`（16 个）此前已纳入。全套 **388 个测试通过**（原 365 + 新增 23）。
> - 注：告警配置持久化未在本切片落地（低优先级，见第 3 节技术债）。

## 5. 第三阶段（⏳ 进行中）：实盘交易执行

**目标**：把只读信号工具升级为**可上生产实盘跑交易**的系统。最高原则是**真实资金安全**——任何能下单的代码，bug 即亏损；套利交易的头号风险是「双腿原子性」（一腿成交、另一腿失败 → 单边裸敞口）。

**执行策略（稳妥路线）**：半自动（机会 → 人工确认 → 下单）+ 先 dry-run（真实 API 只读连通 + 模拟下单，不动真钱）+ 单平台起步（Kalshi 首发）。

> 设计取向：新增一个与现有只读架构**对称的「执行半边」**。现有 `PlatformAdapter` 是读边界；新增 `ExecutionAdapter` 作为写边界。先用 `PaperExecutionAdapter`（模拟盘）打通全链路，真实下单延后接入且默认 dry-run。

### 切片划分（按依赖与风险优先级排序）

#### 切片 E：交易域模型与执行边界（✅ 已完成 · 奠基）
- [x] 定义交易域模型：`Order`、`OrderStatus`、`Fill`、`Position`、`TradePlan`（一个套利机会对应的双腿计划）。
- [x] 定义 `ExecutionAdapter` 接口（写边界）：`place_order` / `cancel_order` / `get_order` / `get_balance` / `get_positions`，统一错误类型 `ExecutionError`。
- [x] `PaperExecutionAdapter`：内存模拟盘，按注入的成交逻辑模拟下单/成交/持仓与余额，支持注入「部分成交/拒单」场景以测双腿失败。
- [x] 单元测试 + 一致性套件（任何执行适配器都必须通过）。

#### 切片 F：套利执行引擎与双腿原子性（✅ 已完成 · 核心风险控制）
- [x] `ExecutionEngine`：把一个 `ArbitrageOpportunity` 转成 `TradePlan`（双腿），按计划顺序下单并跟踪状态。
- [x] **双腿原子性**：一腿失败时的处理策略——尝试撤销/对冲已成交腿，绝不放任单边裸敞口；记录补救动作与残余敞口告警。
- [x] **持仓与订单状态跟踪**：持久化订单与计划（`TradeStore` 接口 + 内存/SQLite 实现，复用存储模式），支持查询与审计。
- [x] 单元 + 集成测试：双腿全成、一腿失败回滚、部分成交、平仓失败留残余敞口、缺适配器等路径，全部确定性可测。

#### 横向插入：predict.fun 行情适配器 + 跨平台金标准关联匹配（✅ 已完成）
- [x] 新增 predict.fun **只读行情适配器**（`adapters/predictfun.py`，建在 BNB Chain 的链上预测市场：off-chain CLOB + 链上结算，二元 YES/NO、价格 0–1），满足 `PlatformAdapter` 一致性套件；`app.py` 的 `ADAPTER_FACTORIES` 注册 `"predictfun"`。
- [x] **跨平台金标准关联**：`CanonicalMarket.cross_refs` 记录平台自报的对端市场标识；`matching.py` 据此短路给满分置信度（`_cross_referenced` / `composite_score` 返回 1.0 / `Blocker` xref 分块键）。即使标题措辞与 Polymarket 完全不同，只要 predict.fun 自报 cross_ref 指向 Polymarket 的 conditionId，就能以置信度 1.0 精确匹配。
- [x] 端到端演示：Polymarket + predict.fun 跑通 行情 → 匹配 → 套利（净利润率 17.65%）→ 模拟盘双腿执行（`COMPLETED`，无残余敞口）。
- [ ] **后续第二步**：真实链上下单（Polymarket / predict.fun，需钱包私钥 + EIP-712 签名 + 真实资金）的执行适配器。
- 注：Kalshi 真实交易暂缓（等风控切片 G 落地）。

#### 切片 G：风控（下单前的最后闸门）
- [x] `RiskManager`：下单前校验——单笔/单市场/总敞口上限、可用余额充足、滑点保护（实际可成交价偏离信号价超过阈值则放弃）、信号新鲜度（过期信号不交易）、最小净利润率门槛。逐条独立校验、可解释决策（`RiskDecision`），核准规模取各上限余量最小值。

- [x] 配置项：`config.yaml` 的 `risk:` 段（敞口上限、滑点阈值、是否 dry-run、是否需人工确认），映射到 `RiskLimits`。
- [x] 单元测试：每条风控规则的放行/拦截边界（`test_risk.py` 21 个 + 执行引擎 dry-run 2 个）。
- 注：风控闸门已就绪并可独立评估；与人工确认流（切片 H）、真实执行适配器（切片 I）的编排接线在后续切片完成。
